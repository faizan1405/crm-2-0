# CRM V2 — Checkpoint B2B1 Data-Contract Audit & Lead Pilot Architecture

> **Status:** Checkpoint B2B1 (`feat/b2b1-lead-api-pilot`), extended in Checkpoint B2B2 (`feat/b2b2-followups-pilot`)  
> **Scope:** Field-level and workflow-level compatibility audit between CRM V2 frontend models (`src/lib/crm/*`, `src/routes/leads*`, `src/routes/follow-ups.tsx`, `src/components/crm/*`) and B2A backend REST contracts (`src/server/crm/*`, `src/server/http/crmRoutes.server.ts`), plus the isolated dev-only Lead & Follow-ups Pilot architecture.  
> **Non-Goals:** Zero migration of `Deals`, `Payments`, `Projects`, `Inbox`, `Automation Studio`, `Team Management`, `My Performance`, `Analytics`, or `AI Sales Copilot` live OpenRouter in B2B1/B2B2. Browser-local `localStorage` (`scale-flow-crm-2-demo`) and IndexedDB (`scale-flow-payment-proofs`) remain 100% untouched.

## 5. Cross-Module Dependency Impact (`Pipeline`, `My Performance`, `Analytics`, `Data Vault`, `Deals`, `AI Copilot`)

1. **Pipeline (`src/routes/pipeline.tsx` & `src/lib/crm/pipeline.ts`):**
   - Currently computes stage columns, drag-and-drop transitions, stalled flags (`lastStageChangeAt`), and deal creation on `"won"` directly from synchronous `useCRM()`.
   - Also note `GET /api/v1/leads` caps `limit <= 200`, whereas Kanban boards need per-stage grouping/counts and Won -> Deal coordination (B3). Kept on browser-local Zustand in B2B1.
2. **My Performance (`src/routes/my-performance.tsx`, `src/lib/crm/ownerPerformance.ts`) & Analytics (`src/routes/analytics.tsx`, `src/lib/crm/analytics.ts`):**
   - Depend jointly on `leads`, `deals`, `payments`, `followUps`, `activities`, and `goals` in one coherent dataset so pipeline conversion rates and revenue match collected INR totals.
   - Partial server-lead hydration into Analytics/Performance would create split-brain math. Kept local in B2B1 until B2B2–B4 bring server Follow-ups & Deals/Payments online.
3. **Quotation & Won Deal Side Effects (`deals` & `payments`):**
   - Changing a Lead to `"won"` in Pilot updates `crm_leads.status = "won"` cleanly on the server without creating local `deals[]` in Zustand (preventing orphaned local deals pointing to synthetic MariaDB IDs). Full Won -> Deal & Payment proof migration belongs to B3.
4. **Data Vault (`src/routes/data-vault.tsx`):**
   - Exports/imports JSON snapshots of `scale-flow-crm-2-demo` + IndexedDB proof blobs (`scale-flow-payment-proofs`).
   - Completely isolated from Pilot mode; Owner's browser-local records remain intact and inspectable on `/data-vault`.
5. **AI Sales Copilot (`src/routes/ai-copilot.tsx`) & Calls / WhatsApp:**
   - Local routes read `useCRM()`; B5 implements server AI & `/api/v1/calls`, B4/later handles messaging. Therefore, Pilot Lead detail hides or visibly disables **Ask AI**, **Prepare Call with AI**, **Call / Log call**, **WhatsApp**, **Follow-up**, **Assign**, **Tags**, **Custom fields**, **Saved Views**, and **Bulk Add** with clear `B2B1 Pilot` status notes so users never accidentally write to local storage.

## 6. Security, Date/Time & Data-Isolation Guardrails

1. **Dev-Only Server Gate (`DEV_LEAD_PILOT`):**
   - `NODE_ENV=production` **unconditionally disables Pilot mode on the server** (`isLeadPilotAvailable(env)` returns `false` even if `DEV_LEAD_PILOT=true` is set in env or `?pilot=1` / `sessionStorage` is forced on the client).
   - In non-production (`NODE_ENV !== "production"`), Pilot mode requires `DEV_LEAD_PILOT=true` in server env **plus** explicit client opt-in (`?pilot=1` or explicit dev switcher button using tab-scoped `sessionStorage`).
2. **Zero Local-Storage / IndexedDB Contamination:**
   - Route entries (`leads.tsx`, `leads_.$id.tsx`, `leads_.bin.tsx`, `follow-ups.tsx`) resolve SSR/hydration auth & feature flags via `AuthSsrProvider` + `useResolvedAuthState()` and gate `<Local*>` / `<Shell>` behind both `pilotActive` and `pilotResolved` (`AppShellSkeleton` while `sessionStorage` opt-in is unresolved), while `Shell` gates `usePreferenceEffects(authStatus === "authenticated")` so `useCRM.persist.rehydrate()` and `startAutomationRunner()` never execute in Pilot mode or while unauthenticated.
   - `PilotShell` provides Dev Pilot navigation across `/leads`, `/leads/bin`, `/leads/$id`, and `/follow-ups` plus an `Exit Pilot` control (`?pilot=0`) without loading `src/lib/crm/store.ts`.
   - Pilot components (`src/components/pilot/*`) import only pure helpers/primitives (`format.ts`, `validation.ts`, `leadtools.ts`, `crossTab.ts`, `dates.ts`, `types.ts`, `ShellPrimitives.tsx`) and never import `src/lib/crm/store.ts`.
3. **Date/Time Semantics (`Asia/Kolkata`):**
   - Server stores `DATETIME(3)` in UTC and returns UTC ISO strings (`...Z`).
   - Date filters (`createdFrom` / `createdTo`) use `YYYY-MM-DD` IST boundaries (`istDayBoundsUtc` on server).
   - Client formats display times using explicit `timeZone: "Asia/Kolkata"` via `src/lib/crm/format.ts` / `src/lib/api/schemas.ts` rather than depending on the OS local timezone.
4. **Failure & Retry Discipline (`src/lib/api/client.ts`):**
   - `credentials: "same-origin"`, `cache: "no-store"`, timeout protection (`AbortController`).
   - Safe retries ONLY on `GET`/`HEAD` or mutations carrying an explicit `Idempotency-Key`. Unkeyed `POST`/`PATCH`/`DELETE` never auto-retry.
   - `401 Unauthorized` clears client auth state (`clearClientAuthState()`) and redirects cleanly to `/login`.
   - `503 Service Unavailable` / network errors never fall back to `localStorage` and preserve unsaved user form drafts on screen.
5. **MariaDB Schema Hardening (`0002_b2b1_widen_idempotency_scope.sql`):**
   - Live MariaDB E2E verification caught that `crm_idempotency_keys.scope` (`varchar(48)`) truncated entity-scoped idempotency keys (`lead:update:<id>` is 53 chars; follow-up/activity scopes reach 57 chars).
   - Fixed in `src/server/db/schema.server.ts` by widening `scope` to `varchar(128)` with forward Drizzle migration `0002_b2b1_widen_idempotency_scope.sql` and a dedicated schema length test in `src/server/b2a-core-crm.test.ts`.
